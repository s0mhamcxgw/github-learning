# 编程实操课的笔记与代码

仅在本节实际涉及代码、调试或项目练习时使用。沿用课程Skill的来源核对、时间点、仓库与增量更新规则；大纲课和纯概念片段保持正常学习笔记。

## 先核对代码来自哪里

优先读取用户提供的课程源码、讲义、Notebook和跟敲项目，并核对课时、文件、版本及上下文；它们是不同的来源，不能互相冒充。配套资料需要登录、领取或授权而当前未提供时，说明所缺材料，不代替用户注册、发消息或绕过限制。

能读取视频画面或截图时，按讲解中的关键时间点核对屏幕代码，关注缩进、符号、文件名、导入和前后修改。音频转写能解释思路，不能可靠还原所有代码；看不清的部分标“待核对”，不靠常识补成老师原代码。时间点须来自实际视频、字幕或音频片段。

将代码明确标为以下来源，按实际情况提供，不为每课机械创建三个版本：

| 来源 | 记录要求 |
| --- | --- |
| 课堂原代码 | 能回到已读取的源码或视频片段；若是课堂阶段性代码，注明可能尚未完整。 |
| 校正或兼容版本 | 保留原来源，说明改了哪里、为什么改，以及是否实际验证；涉及变化的库/API时核对相应版本的官方文档。 |
| 自编学习示例 | 标“非课程原代码”，说明演示的概念，不据此宣称已取得课堂源码。 |

用户的跟敲文件、注释和练习答案属于用户内容。优先保留并增量解释；调试时采用必要的小改动，保留原始版本或差异。若关键源码缺失，先完成可核实的课程解释，再提出一个具体的材料需求；只有用户允许或需要补充说明时才另给自编示例。

## 代码与笔记分别放在哪里

笔记写入本次指定的Obsidian课程库。已有代码项目沿用原位置、结构和解释器，不搬到笔记库，也不批量重写。未指定代码位置时，在当前E盘课程项目的 `outputs/course-code/<课程ID>/Pxx-课题/` 保存本次示例；任务脚本、中间材料和运行日志放项目 `work`。

按内容选择文件类型：脚本和模块用 `.py` 等源文件，分步实验或数据分析可以沿用 `.ipynb`；尊重用户正在使用的形式，不为展示而强制转换。跨课项目沿用同一工程，笔记标清当前课新增或修改的文件及依赖的前课内容。

在笔记中给出代码目录、入口文件和可定位的文件链接；库外代码不要写成无法解析的Wiki链接。短而关键的代码可放带语言标记的代码块，完整项目保存在代码文件中；笔记说明代码片段对应哪个文件或单元格，避免两份内容悄悄不一致。临时缓存、虚拟环境和大数据文件不放入笔记目录。

## 环境与运行信息记录到能复现的程度

只记录本节需要的内容：

- 实际解释器/运行时及版本；使用哪个现有项目或虚拟环境。
- 本节用到的第三方依赖和已核实版本，标准库与第三方库分清；不凭一条import编造完整依赖清单。
- 入口文件、工作目录、运行命令或Notebook单元执行顺序。
- 所需数据、文件位置、输入条件与来源；前课生成的文件未取得时明确缺失。

优先复用适合的现有环境。确需安装时使用项目隔离环境，并记录实际操作；不因整理课程擅自升级全局Python、改动其他项目依赖或IDE全局配置。示例需要凭证、付费接口、外部写入或其他额外副作用时，按用户本次授权处理；缺条件时记录阻塞，不把“整理笔记”解释为这些操作的授权。笔记与代码不保存明文密钥，使用配置项名称或占位符说明所需设置。

## 怎样讲代码才方便复习

围绕本节任务说明：输入是什么、各段代码负责什么、关键变量或对象如何变化、输出是什么，以及与所学概念的关系。按功能段解释；只有用户需要或某行确实关键时才逐行讲，不把每行代码换成一句同义中文。

区分老师实际演示的步骤与助手额外讲解。对于面向对象、算法等课程，可用本节代码追踪对象状态、函数调用或数据变化；没有实际代码的片段不强行加程序。记录常见错误时，只把实际遇到或课程明确展示的错误记成“本次错误”；额外提示应标为可能问题。

## 实际验证与报错记录

对助手新增或修改、准备交付为可运行的代码，选择与改动相称的小规模实际检查；已有未修改的材料不必为了填表而全部重跑。先检查代码的输入、文件与副作用，再执行授权范围内的部分。保留实际使用的输入、命令、关键输出或错误摘要；日志放 `work`，笔记链接关键证据。

| 证据状态 | 可以怎样表述 |
| --- | --- |
| 课程画面、讲义或Notebook保存输出 | “课程展示/文件中保存的输出”；未证明在本机重跑成功。 |
| 仅阅读或静态检查 | 说明实际检查内容；语法通过不等于依赖、数据和逻辑均正确。 |
| 助手在本机执行 | 列明输入、实际结果与覆盖范围；单个例子通过不等于所有情况正确。 |
| 仍缺源码、环境、数据或凭证 | 标“未运行/部分验证”，说明具体缺口；不以预期输出代替实际结果。 |

Notebook的旧输出和执行计数不代表当前代码可从头运行。需要验证时，在适当副本或授权范围内检查单元依赖，分清保存结果与本次重跑结果。

实际报错记录按“触发步骤与关键错误 → 原因依据 → 修改 → 重新验证结果”组织。无法确定原因就保留待验证判断；首次失败后没有重跑，不写已解决。不要为了制造学习记录而故意引入错误，也不要把助手的修复经历写成用户已经掌握。

## 练习与学习进度

给一道与本课知识相近、规模合适的练习，或沿用用户正在做的课后题。默认先给题目、必要输入和验收标准；用户要求讲答案、示范或卡住时再按其要求提供提示或完整解答。助手验证用的结果不混入用户的练习答案。

将“笔记已整理”“助手示例已验证”与用户的学习状态分开。用户进度可记录为看过、跟敲成功、能解释、能独立完成，但必须来自用户明确反馈或其实际提供的过程；不强制每课逐级升级，不自动勾选。

## 组织与交付

通常按“本节目标与回看点 → 关键概念及代码解释 → 代码文件与运行方法 → 实际结果或问题 → 练习与自己的理解”组织，依实际内容增减，不为无代码课生成空环境表和空报错表。

交付前核对：课时和来源、代码文件与笔记的一致性、环境和输入是否说清、执行证据是否支持所写状态、报错是否真的复验、文件链接是否可用，以及用户原有注释/答案是否保留。学习日志记录本次新增代码及实际验证范围。

调用示例：`用 $course-study 整理这节编程课，解释课堂代码，关联E盘代码文件，记录环境、实际运行结果和报错；最后给一道练习，先不提供答案。`
